# OpsForge

Lab that provisions a **distributed environment spread over simulated distant sites** (multi-cloud /
multi-region) on one Linux host, with realistic WAN conditions and minimal RAM. Read `docs/PLAN.md` before
structural changes; it has the phases, acceptance criteria and design decisions.

Current status: **Phase 8 done** (2026-10-23): per-node `cluster:` (default `lab` = Phase 4's stretched cluster);
`topologies/multi-cluster.yml` (one cluster per site, via `OPSFORGE_TOPOLOGY`) linked by Skupper 2.2.3 (site per
cluster in namespace `mesh`, nodeport link access over the VPN, link cost = RTT); scenario `cluster-failover` (2 failed
requests when the serving cluster is lost); multi-cluster idles at 4450 MiB anon+kernel, pool 12 GiB.
**Phase 7 done** (2026-10-23): optional `ci` node (role `ci`, site a): Gitea 28 + Actions, one
`gitea-runner` in host mode building with buildah, `docker-registry` over TLS with the node's lab certificate; Flux
(source + kustomize controllers) applies Gitea's `opsforge/deploy` repo; the pipeline commits each image tag there.
Reference workload `webapp` (Go + PostgreSQL in region a) at `/app` on every site's ingress; scenario `ci-rollout`
(push → all sites in ~1 min); 2217 MiB anon+kernel idle with CI, pool 8.95 GiB.
**Phases 5 and 6 done** (2026-10-23): monitoring node `mon` (VictoriaMetrics + Grafana, exporters everywhere,
blackbox probes per site pair from each gateway, three dashboards); fault commands `degrade`/`mtu`/`flap`
and the scenario runner (`scenarios/*.yml`, 5 scenarios passing); 1635 MiB anon+kernel idle, pool 6.47 GiB.
Phase 4 done: stretched K3s v1.37.1 in **unprivileged** containers (profile `k3s-node`), flannel vxlan inside the
VPN, per-site Traefik ingress, zot cache `opsforge-cache`, `opsforge kubectl`. Phase 2.5 done except **reboot
survival** (needs a host reboot by the user). **Next:** not planned yet (open: geo-aware DNS, Windows nodes,
the reboot-survival check).

## Host facts that drive the design

- Arch Linux, 12 threads, 14 GB RAM, ext4 root (~59 GB free): RAM is the tight resource. Prefer the lightest
  option and measure (`./opsforge smoke` prints idle container memory). Measured: Debian 13 container idles at
  113 MiB. Incus storage pool `default` is btrfs on a sparse loop file capped at 25 GiB.
- **Partial-upgrade state**: the pacman DB is synced but ~729 updates are not installed. Don't `pacman -S` new
  packages until the user has run `pacman -Syu` (+ reboot); the local `shellcheck` is broken because of this, so
  the Makefile falls back to the `koalaman/shellcheck` Docker image.
- **incus-admin group and tmux**: the user's tmux server predates their `incus-admin` membership, so new panes
  lack it. If `incus` reports permission denied, the user must run `newgrp incus-admin` then `claude --continue`
  (or restart tmux). `sg` is not installed.
- `sudo` needs a password: never run privileged commands yourself. Put them in `scripts/host-setup.sh` (or a new
  root script) and ask the user to run it with `! sudo ...`.
- Docker is installed and running. Its iptables `FORWARD` DROP policy drops Incus bridge traffic unless
  `opsforge-docker-user.service` adds `DOCKER-USER` accepts for `incusbr+` and `of-+`.

## Conventions

- **Network naming/addressing**: lab Incus networks are prefixed `of-` (interface names ≤ 15 chars, so site ids
  ≤ 6 chars). Never reuse reserved ranges: `10.99.0.0/24` (incusbr0), `172.17.0.0/16` (docker0),
  `10.42.0.0/16`/`10.43.0.0/16` (K3s). These are enforced in `RESERVED_NETS` in `opsforge`; keep it in sync
  with `lab/host/incus-preseed.yaml`.
- Link semantics: `rtt` is round-trip (applied rtt/2 per direction); `jitter` is RTT stddev (jitter/√2 per
  direction); `loss`/`rate` are per direction. netem always gets a `rate` so jitter cannot reorder packets.
- Lab wiring (docs/PLAN.md §3 "Wiring"): bridges `of-<site>` (VPC) and `of-<site>-wan` (gateway↔wan-core),
  no host addresses on either. Routers are `wan-core` and `<site>-gw`; gateway is VPC `.1`, nodes `.11`+.
  Lab instances are tagged `user.opsforge.role` (and `.site`); `down` deletes those plus managed `of-*` networks.
- `up` is incremental: it compares each instance's `user.opsforge.spec` with `render.fingerprint()` and
  rewires + re-pushes + restarts only what changed (see `docs/PLAN.md` Phase 2.5). Anything new pushed into an
  instance must go through `Instance.files`/`nics` so the fingerprint sees it. The spec is taken from `topology.yml` before
  wan-core's files are merged with live link state, so `link` edits never count as changes.
- `incus` subprocesses get stdin `/dev/null` (`incus()`): some commands read YAML from a non-tty stdin and hang.
- Routers are configured only by generated files pushed before first boot; their boot script logs to
  `/var/log/opsforge.log`. Change `ROUTER_BUILD`/`NODE_BUILD` → bump `ROUTER_IMAGE`/`NODE_IMAGE`'s suffix so `up`
  rebuilds it; `opsforge gc` then deletes the old one.
- Split of ownership: opsforge/render owns addressing, firewalls, sshd host keys and bastion forwarding (pushed
  before boot, so Ansible can connect at all); Ansible owns services and OS config. Ansible never touches wan-core.
- SSH path: host → `incus exec wan-core -- nc` → gateway public IP → `ProxyJump` → node. Unshaped (wan-core's
  own traffic). Stale `ControlMaster` sockets in `.opsforge/ssh/` can keep old sshd settings: `ssh -F
  .opsforge/ssh/config -O exit <host>`.
- VPN (Phase 3) is rendered like the rest of router config, not by Ansible: `wg-<peer>` interfaces (UDP port
  `51820 + peer's index` in `topology.yml`'s sites), `/etc/opsforge/wg/*.conf`, `/etc/bird.conf`. Only the site
  listed first has the peer's `Endpoint`: two initiating sides collide and stall for up to ~40 s at boot. Keys:
  `.opsforge/wg/<site>.pem` (openssl X25519). `render.plan()` without keys renders placeholders (tests, `render`);
  commands that push to instances use `lab_plan()`.
- K3s (Phase 4): nodes with a `k3s-*` role get profile `k3s-node` (unprivileged, nesting, `/dev/kmsg`, modules
  loaded by Incus); keep it unprivileged. Ansible role `k3s` installs the binary from `.opsforge/k3s/` (no
  install script), configures `/etc/rancher/k3s/{config,registries}.yaml` + `flannel.json`; server manifests go in
  `/var/lib/rancher/k3s/server/manifests/opsforge-*` (K3s applies them). Flannel's `Backend.MTU` is the underlay
  MTU (flannel subtracts 50 itself) and an existing `flannel.1` is never resized. Spread constraints act only at
  scheduling: deploy spread workloads after all nodes are Ready, and avoid `minDomains` with `nodeTaintsPolicy:
  Honor` (blocks rescheduling during a partition). `opsforge kubectl` = host kubectl + forward to 127.0.0.1:6443
  (`K3S_API_PORT` ↔ `k3s_api_port`); `verify` reads the demo by `DEMO_NAMESPACE`/`DEMO_APP`.
- Image cache `opsforge-cache` (zot, `10.99.0.2` on incusbr0, reached by the lab at `203.0.113.2:5000` via
  wan-core DNAT) is **not** a lab instance: no role tag, no profile; `down` keeps it, `down --purge` deletes it.
  zot needs `http.compat: ["docker2s2"]` or Docker-format images bypass it silently (containerd falls back).
- Faults (`partition`, `degrade`, `mtu`, `flap`) store the live link state from before the first fault in
  `wan-core:/etc/opsforge/pre-fault.json`; `heal` restores it. `link` edits are not faults (kept until `--reset`).
  A link's `mtu` is a silent black hole (nft table `opsforge_mtu` on wan-core, rendered in `links.sh`).
- Monitoring (Phase 5): `mon` scrapes everything at private addresses over the VPN; gateways' firewalls (render)
  accept 9100/9115 from it, so it needs `interconnect: vpn`. Scrape config `ansible/roles/monitoring/templates/
  scrape.yml.j2`; dashboards are JSON in `files/dashboards` (provisioned, read-only in the UI: edit the files).
  VictoriaMetrics needs `-search.latencyOffset=0s` or the latest 30 s are invisible to queries. Grafana's .deb is
  cached in `.opsforge/cache/` (its CDN is slow). In Jinja, build host lists with `+`, never `union` (set order
  changes between runs, so templates churn and break `changed=0`).
- CI (Phase 7): a node with `role: ci` is the opt-in (one at most; needs a k3s-server and `interconnect: vpn`). The
  role seeds Gitea's `webapp` and `deploy` repos from `roles/ci/files/webapp` and `templates/deploy` **only while they
  are empty**: afterwards Gitea is the source of truth, so change the live deploy repo with a commit (Flux applies
  it), not by editing the templates. Workflows run in host mode (`runs-on: lab`): no `uses:` actions (they need Node
  and github.com); topology-dependent values are Actions variables set by Ansible (`ci_variables`), the deploy push
  uses user `ci-bot`'s password as a secret. buildah needs `--isolation chroot --network host` and `netavark`
  installed; base images come through the zot cache (`registries.conf.d/50-opsforge.conf`). Gitea writes to
  `app.ini` any secret it lacks (fails, file is read-only): every secret incl. `oauth2.JWT_SECRET` comes from
  `.opsforge/ci/`. Spread constraints of rolled-out workloads need `matchLabelKeys: [pod-template-hash]`, or a
  rollout piles new pods where old ones are being removed. Gitea and Grafana both use port 3000: forward one with
  `--local` (the scenario uses `forward ci:3000 --local 13000`). Ports `CI_GITEA_PORT`/`CI_REGISTRY_PORT` ↔
  `ci_gitea_port`/`ci_registry_port`; the k3s role's `k3s_gitops_url` repeats the port and repo names.
- Node exporter (Debian) pulls in `prometheus-node-exporter-collectors`; its apt timer (a Python apt-cache load every
  15 min) is masked: it tipped mon past 512 MiB into a thrash during a provision.
- Multi-cluster (Phase 8): everything K3s is keyed by cluster: `render.k3s_clusters()` (server, nodes, sites,
  `api_port` = 6443 + index) → inventory `lab_clusters`, per-node `lab_cluster`; role vars `k3s_cluster`,
  `k3s_server_host`, `k3s_cluster_nodes`. Never use `groups['k3s_server'][0]` as "the" server. `opsforge kubectl
  --cluster X` (before kubectl's args), `.opsforge/kubeconfig-<cluster>`. A node's K3s role/cluster change makes `up`
  recreate it (`k3s_identity_changed`). Skupper: `ansible/roles/k3s/tasks/skupper.yml` (only with >1 cluster); the
  release manifest's controller env is edited with `regex_replace` (plain `replace` with `'\n'` never matches in
  Ansible); links created by name `link-<peer>-*`. Connector `host:` must be an FQDN with a trailing dot: otherwise
  the lookup walks the nodes' `*.lab` search domains and a partitioned site's zone stalls every new connection by
  seconds. Servers in multi-cluster need 2 GiB (≈1.2 GiB anon each; 1.5 GiB thrashed). `verify --mem/--disk`
  defaults are per layout (`MEM_CEILING_MIB`/`DISK_CEILING_GIB` dicts, `scenario.layout()`).
- Scenarios: `${node:<site>}`, `${server:<site>}`, `${cluster:<site>}` resolve per layout (never hard-code `b-w1`);
  `layout: stretched|multi-cluster` skips a scenario on the other layout.
- Scenario files: step keys must not be YAML 1.1 booleans (`on`, `yes`, ...): `run` takes `host:`, not `on:`.
- Gateways' memory limit is 128 MiB (Ansible's Python OOMs at 64); limits are ceilings, idle use is ~5 MiB anon.
- Ansible `copy` content can't use `{{ ansible_managed }}` (templates only); use the literal "Managed by Ansible"
  header. Lint: ansible-lint `production` profile must pass (`make check`).
- Live link state is `wan-core:/etc/opsforge/links.json`; `verify` checks against it, not `topology.yml`.
  `link --save` edits the link's single line in `topology.yml` by regex, so keep each link on one flow-style line.
- Memory budget = anon + kernel from `memory.stat` (`verify --mem`), never Incus' usage figure (includes page cache).
- Services on routers start before `opsforge.start` assigns addresses: bind dynamically (dnsmasq `bind-dynamic`).
- Never capture output (pipes) from `ssh -f`: it and its ProxyJump child keep stderr open after backgrounding,
  so `subprocess.run(capture_output=True)` hangs. `start_forward` writes stderr to a temp file instead.
- Killing a provision run leaves ControlMaster sockets in `~/.ansible/cp/` and `.opsforge/ssh/cm-*`; after
  restarting an instance they hang the next run: kill those ssh processes and delete the sockets.
- Values duplicated between files must stay in sync: modules (`lab/host/modules-load.conf` ↔ `REQUIRED_MODULES`),
  sysctls (`lab/host/sysctl.conf` ↔ `REQUIRED_SYSCTLS`), the KSM NodePort (`k3s_kube_state_metrics_node_port` ↔
  `monitoring_ksm_node_port`), exporter ports (`render.NODE_EXPORTER_PORT`/`BLACKBOX_PORT` ↔ `monitoring_*_port`),
  VictoriaMetrics/Grafana ports (`VM_PORT`/`GRAFANA_PORT` ↔ `monitoring_vm_port`/`monitoring_grafana_port`).
- Shell: bash, `set -euo pipefail`, tabs, must pass shellcheck. YAML must pass `yamllint` (`.yamllint`).
- After finishing a phase: tick it in `docs/PLAN.md`, record a measured RAM snapshot, update these CLAUDE.md files.
- Commit messages: `feat(<scope>): <message>`. Default branch: `master`.

## Verify

```bash
make check            # lint + topology validation (needs host-setup's dev tools)
./opsforge preflight  # host readiness
./opsforge smoke      # Phase 0 acceptance: container boots, gets IP, reaches the internet
./opsforge up && ./opsforge provision && ./opsforge verify   # Phases 1-2 acceptance (--quick skips iperf3)
./opsforge provision   # again: must report changed=0 on every host
./opsforge kubectl get nodes   # Phase 4: K3s from the host (verify also checks nodes, spread and per-site ingress)
./opsforge scenario --list     # Phase 6: every scenario must pass (./opsforge scenario <name>)
./opsforge scenario ci-rollout # Phase 7: a push builds, pushes and rolls out to every site
export OPSFORGE_TOPOLOGY=topologies/multi-cluster.yml   # Phase 8: down, up, provision, verify, then:
./opsforge scenario cluster-failover   # the serving cluster is lost; the service survives
```
